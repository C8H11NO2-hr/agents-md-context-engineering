# 分层 AGENTS.md 文件设计原则

分层 AI 指令文件只有在被当作**上下文架构**、而不是团队所有偏好的堆砌场时，才能发挥最大作用。

## 1. 将上下文放在工作附近

根文件应说明整个项目。模块文件应说明该模块。测试文件夹文件应说明测试应如何编写。

良好的局部指令包括：
- 领域不变量。
- 从代码中不易看出的命名规则。
- 安全或正确性陷阱。
- 本地测试命令。
- 团队明确拒绝的模式。

根 `AGENTS.md` 应回答：
- 这个项目是什么？
- 使用什么技术栈？
- 什么不应随意改动？
- Agent 应如何验证工作？
- 更深层的规则应在哪里找到？

如果根文件变得过大，将材料移入 `docs/` 或一个局部的 `AGENTS.md`。

## 3. 优先使用约束而非偏好

“使用清晰的命名”是弱指令，因为它不改变行为。“所有外部 API 错误在离开服务层之前必须转换为 `DomainError`”是强指令，因为它告诉 Agent 如何行动。

当人类反复纠正 AI 生成的模式时，更新最近的 `AGENTS.md`。

示例：**变更说明** —— 不要在集成测试中模拟仓库接口；使用 `tests/fixtures` 中的内存存储。

这将审查反馈转化为项目记忆。每条指令都有成本。移除那些：
- 已由代码或测试强制执行的规则。
- 过于笼统、不影响输出的规则。
- 在许多文件夹中重复的规则。
- 重构后不再成立的规则。

## 6. 显式声明冲突

如果子文件夹有意覆盖父级规则，请直接说明。

**局部覆盖** —— 根项目偏好 JSON 日志。此 CLI 文件夹使用纯文本日志，因为输出由终端中的人类消费。

## 7. 像审查代码一样审查指令变更

指令文件塑造未来的实现工作。修改 `AGENTS.md` 的 Pull Request 应解释：
- 变更解决了什么反复出现的问题。
- 它影响哪个文件夹或工作流。
- 团队如何判断它是否有帮助。
